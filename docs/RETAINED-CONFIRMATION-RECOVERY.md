# Recover confirmation from unchanged retained history

Startup reconciliation now checks pending bridge-owned message IDs against the
committed message journal before declaring the profile ready. This is necessary
because unchanged native history produces no new journal delivery event. Without
this step, an old quote migrated to an unconfirmed state could remain uncertain
even when retained history already contained its send confirmation.

The recovery step reads only IDs associated with the profile's outbox requests
and quote companions. It checks the chat, message ID, outbound direction, sender
identity, and sent/delivered/read evidence before recording confirmation. Local
insertion alone, inbound messages, or another sender cannot acknowledge the work.
Text, attachment, and companion quote confirmation are handled independently.

It visits sequence-cursor pages of 100 requests, yielding between pages and
honoring cancellation. Confirmed rows may leave the recovery list during the
scan without causing later rows to be skipped. Repeated scans are idempotent.
No send, upload, or Matrix event is generated by the recovery step.

The synchronizer commits the profile snapshot first, switches its incoming
watchers to normal journaling, and then awaits confirmation recovery. Outbound
delivery and failure notices remain gated until recovery succeeds. A failure
keeps readiness false and follows the existing resynchronization retry path;
live events arriving during that interval still enter the journal normally.

Tests reproduce the original startup failure using already-acknowledged journal
changes, verify no new Matrix replay work, check invalid confirmation evidence,
and traverse 105 text requests plus 105 independent quoted attachments. Separate
tests cover cancellation, callback failure/retry, and live events arriving during
the recovery callback. All 18 focused tests pass on Mac and both Linux runtimes;
Linux uses changed-source mounts with network disabled and no account data.

This uses retained canonical evidence; it does not establish native task/upload
resumption or recipient delivery beyond the recorded timestamp. Old rows already
marked confirmed by buggy earlier versions remain outside the pending scan.
The new recovery changes still need package rebuild/export and live rollout.
